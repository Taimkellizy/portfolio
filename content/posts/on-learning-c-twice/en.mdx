I learned C twice. The first time was safe — problem sets, a grade, a feeling
of completion. The second time happened months later, when I opened a real
codebase and realized the language I "finished" was a language I had only
visited.

## First pass

CS50x does something most courses don't: it puts you inside the machine's
room. Week after week, the lectures peel the abstraction away — ASCII, memory,
the stack — until you're looking at pointers without makeup.

And I nodded along. I could draw the boxes and arrows on paper. I could pass
the check50 tests. What I couldn't do yet was *read* memory the way the
lecturer did: as a continuous grid where every variable is just a named
address and every address is fair game.

### The ampersand

```c
int x = 42;
int *p = &x;

printf("%i\n", *p); /* 42 — but which one? */
```

That snippet looks trivial. It hid a question I couldn't answer yet: *what is
`x`, physically?* I would have said "an integer." That's the answer the quiz
wanted. It's also wrong.

## Three lessons

Three things only landed the second time, and all of them are the same
lesson at different depths.

### Pointers

Pointers are not "references to values." They are values — integers that
name an address — and C lets you do arithmetic on them because addresses are
just numbers in a grid. The `*` in the declaration and the `*` in the
expression are two different ideas wearing the same symbol, and most confusion
about pointers is confusion about which one you're looking at.

### The stack

Every function call carves a frame out of it, and when the function returns,
the frame is reclaimed — not "destroyed," not "cleaned up." Reclaimed. The
bytes are still there; the *ownership* is gone. This is why returning a
pointer to a local variable is a bug, and why the bug works most of the time:

```c
char *greet(void) {
    char name[16] = "taim";
    return name; /* compiles. mostly works. always wrong. */
}
```

### Ownership

In C nothing watches you. `malloc` hands you memory and trusts you to give it
back exactly once. Languages I used later — Python, TypeScript — turned that
discipline into rules. Understanding C first made those rules legible instead
of magical.

## What worked

The course's real trick is that it never lets C stay abstract.

### The habit

The famous "swap" exercise, the memory diagrams, `debug50`, the valgrind
weeks — they all push toward the same habit: stop asking *what does the
program do* and start asking *what does the memory look like*.

That habit is the whole gift. Rust's borrow checker, JavaScript's event loop,
even CSS stacking contexts — every hard idea I've met since has been some
version of "who owns this, and when does ownership end."

## Second pass

There's a version of learning that ends when the certificate arrives, and a
version that begins there.

### Vocabulary

The first pass gave me the vocabulary. The second — opening real code,
breaking real memory, fixing real crashes — gave me the language.

If you're finishing a course and it feels complete: good. Let it rest, then go
read code written by someone who is angrier than your problem sets. That's
where the second pass lives.
